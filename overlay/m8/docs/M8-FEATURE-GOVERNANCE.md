# M8 功能管理：怎么加东西不打架

问题不是「功能太多」，是**没有边界**：40 个 overlay 文件平铺着，谁都能改、改完也不记账，攒到一定程度就分不清哪条改动属于哪个功能、哪条验过。

下面这套是给「一个人长期迭代一台机器」设计的最小机制，不引流程工具。

## 一、三条铁律

1. **路径即边界**：`overlay/m8/` 里的文件路径必须和 `src/` 下同名文件**完全一致**（覆盖靠路径实现）。禁止另起平行目录（历史上 `packaging/openwrt/root/` 和 `m8-pkg/` 各存一份，已撤销）。
2. **一处改动一处登记**：动任何 overlay 文件，必须在 `docs/M8-CHANGE-LEDGER.md` 里对应一行；新增/删除文件必须同步增删行。
3. **改上游文件必须留痕**：凡是在 src 原版文件上改的地方，第一行注释打 `// M8:`（或 `# M8:`）。上游升级时靠它一眼找出所有改动点。

## 二、先问「能不能不碰上游文件」

新功能按这个顺序选落点，越靠前越好：

| 优先级 | 落点 | 例子 |
|---|---|---|
① | 新增独立文件 | 新的 `internal/audio/xxx.go`、`rpcd/airsim-xxx`、`view/airsim/xxx.js`
② | 挂到已有挂钩点（加几行） | `audio.OnStreamFault = ...`、`admin.HandleFunc(...)`、rpcd 的 `case`、`menu.d`/`acl.d` json
③ | 改上游文件本体 | 只在①②都做不到时才改，且改动越小越好，必打 `// M8:`

①的好处是上游升级时这个文件跟它没关系，永远不会冲突；③每次上游动同一个文件都要重新搬一遍。

## 三、公共插座（多人/多轮改动最容易打架的地方）

这几个点是**多个功能共用的挂钩位**，改之前先翻账本看有没有人在用：

- `internal/audio/session.go` 的 `Bridge` 字段与 `OnStreamFault`（音频功能都抢这个）
- `cmd/airsim-mu300d/main.go` 里 `admin.HandleFunc` 注册段（每个新接口一行）
- `m8-pkg/luci/usr/libexec/rpcd/airsim` 的 `case` 分支（每个网页动作一个分支）
- `luci/usr/share/luci/menu.d/luci-app-airsim.json` 与 `acl.d/luci-app-airsim.json`（加页面要同时加菜单和权限，少一个就是 404 或 403）

规则：**同一个插座一轮只加一处**，改完立刻装机验完再改下一处，不攒批。

## 四、一次改动的完整流程（7 步）

1. **编号**：确定改哪块（音频 / daemon / 后端 / 前端 / 骨架 / agent 补丁 / 文档），起一个账本 ID（如 `C2`）。
2. **选落点**：按第二节的顺序挑，尽量新增文件。
3. **记账本**：先加行（状态写 🟡 代码已改未验），再做代码。
4. **改 + 编**：`sh scripts/build.sh` 合成后交叉编译，两处二进制都要重编（daemon 和 agent），版本串保持一致。
5. **真机验**：装包 → 按验收判据跑 → 留证据（命令输出 / 截图路径）。
6. **改状态**：✅ / 🟡 / ⏸ / ❌ 四态选一个，证据写进账本。
7. **发版**：Release 四段直接从账本生成——「改了什么」取 ✅🟡 行，「未修复问题」取 ❌ 行，「本版未包含」取 ⏸ 行。不用再回忆。

## 五、自动断言（提交/打包前跑一遍）

`sh scripts/check-ledger.sh`：

- overlay 里每个文件必须在账本里出现（防止偷偷加文件不记账）
- 账本里引用的 overlay 文件必须真实存在（防止删了文件忘改表）
- `overlay/m8/VERSION` 与 `m8-pkg/VERSION` 必须一致
- 产物名不能带括号/空格/中文（GitHub 会把括号改成点，上传变空文件）

不通过就不许打包。打包命令改成：`sh scripts/check-ledger.sh && sh scripts/build.sh <out>`。

## 六、上游升级（r22 → r23）怎么走

1. `git archive v0.1.0-r23 | tar -x -C /tmp/src23`，把新原版铺开。
2. 逐条走账本：每个「改上游文件」的行（A1/A2/A3/A5/A6/B1~D1/F4），用
   `git merge-file current 改后版 新原版` 三路合并，或者直接对 diff 手工落。
3. **改不进去就报错停下**，不许静默跳过——上游改了措辞而补丁还在打旧字符串，是最典型的「看着成功、实际没生效」。
4. 合并完重编、装机、跑一遍验收判据，通过后再更新 `upstream/r23/` 与 tag。
5. 补丁类（`patches/*.patch`）同样要 `git apply --check`，报错就是上游文件变了，先看变在哪再决定。

## 七、什么情况算「打架」

出现下面任一情况，说明边界已经破了，先停下来记账、拆开，再继续：

- 同一个文件一周里被三件不相干的事改过
- 修一个功能，另一个功能退化（先查账本里谁在这个插座上）
- 页面上一处文案改了，后端正则没跟着改（同一功能的改动散在两个区）
- 说不清某个 overlay 文件是干嘛用的 —— 账本里没有它，或者描述对不上
