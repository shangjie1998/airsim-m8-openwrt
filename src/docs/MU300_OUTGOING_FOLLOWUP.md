用户另行授权拨打指定测试号码，经过带身份认证的局域网网关只拨一次。
拨号回执校验通过，Agent 和基带中的号码与完整请求一致。只观察控制信令，

| 时间 | 基带原始状态字段（号码省略） | Agent |
| --- | --- | --- |
| 14:09:51 | `+CLCC: 1,0,2,0,0` | dialing |
| 14:09:58 | `+CLCC: 1,0,3,3,0` | 仍为 dialing |
| 14:10:05 | `+CLCC: 1,0,3,3,0` | 仍为 dialing |
| 14:10:06 | Agent 判断通话消失 | 原 ID 被结束 |

**已确认的解析缺陷：基带仍列出通话，解析器却过滤了 mode 3。**
`stat=3` 表示 alerting；第 4 个字段 `mode=3` 不是数据模式。
[ETSI TS 127 007 §7.18](https://www.etsi.org/deliver/etsi_ts/127000_127099/127007/16.12.00_60/ts_127007v161200p.pdf)
将 mode 3/4/5 定义为混合业务的语音阶段，mode 1/2/6/7/8 为数据或传真阶段，
9 为未知。共享解析器原先仅接收 mode 0。

因此 DeepSeek 文档中“基带连续数秒不列出通话”的根因结论尚不成立；
本次直接观察到的是软件把真实存在的振铃记录删掉了。延长缺失宽限不能
修复它，只会延迟客户端结束通话。之前短号码记录是独立输入线索，不是
本次使用完整号码复现的原因。

测试结束后，旧 Agent 已失去 ID，无法通过正常定向 API 清理。先查询确认
基带仅剩本次拨出的同一槽位、同一号码，才发送一次 CHUP；收到 OK，并再查
CLCC 确认空闲。没有操作其他通话。用户随后明确反馈“对方响铃了”；
这验证了原版也能将完整号码呼出，但不等于双向音频验收。

## 本次候选补丁

核心修复：MU300 的 CLCC 解析接收 mode 0/3/4/5，继续排除数据、传真和未知模式。
其他平台仍使用原先的 mode 0 解析规则。拨号、后台轮询和控制前刷新统一使用
该规则，让 dialing(mode 0) → alerting(mode 3) → active(mode 0) 保持同一个 ID。

保留已有的通话建立宽限和拨号幂等逻辑，补齐以下情况：

- dialing 与 alerting 都使用 10 秒缺失确认窗口；已连接通话仍为 4 秒。
  这是连续可靠查询中“通话缺失”的窗口，不是对方接听的最长等待时间。
- AT 超时、异常或无效 CLCC 打断缺失确认计时，不把未知时间算作挂断证据。
- 操作前刷新也保留暂时缺失的身份；实际控制要求新快照包含全部已知通话，
  缺少目标或其他通话时拒绝发命令，防止错误退化为单路 ATA/CHUP。
- 新拨号检查保留中的身份，防止空快照期间误发第二条 ATD。
- 接听确认期间的短暂空快照不会提前删除 ID。
- 已应答的定向挂断/拒接命令，加上目标槽位缺失，可立即结束该目标；
  同时缺失的其他通话继续等待各自的确认窗口。

持续查询失败时只能报告未知，不能保证马上识别真正挂断；超过宽限的
持续空快照仍会结束通话。这些限制不能通过无限延长宽限来掩盖。
