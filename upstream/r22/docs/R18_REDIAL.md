# R18 通话结束通知与立即重拨候选（待实机验收）

> 历史候选记录：R18 未公开发布。用户于 2026-11-03 明确要求将后续工作以 R19 开发预览发布，当前发布范围和未验收项以 [R19 说明](RELEASE_v0.1.0-r19.md) 为准；下文暂停状态保留为当时记录。

2026-11-03 用户明确要求：去掉两分钟限制，对方挂断后由 U30 Air 接收并向 AirSIM 通知结束；本线程不修改 AirSIM 客户端。R18 继续暂停发布，不能把代码测试通过写成实机已修好。

## 当前行为

- **取消同号码两分钟冷却。** 原通话确认结束、基带可可靠查询为空闲后，新操作 ID 可以立即拨打同一号码，无等待计时器或自动拨号任务。
- 同一次操作仍按已认证配对身份与 `operation_id` 持久去重。已确认的旧请求返回原回执/终态；提交未知不重发 ATD。新编号仍需实际空闲，不允许并发第二路拨号。缺少操作 ID 的拨号明确拒绝，不以号码猜测身份；已检查的 iPhone 158 canonical 路径和 LuCI 路径均带该字段。
- 新策略不再把“号码相同”当成自动重试的证明。若其他客户端主动更换操作 ID 或换身份再次提交，设备无法单靠号码区分人工动作；不能宣称所有旧客户端的错误重试都被消除。跨路由身份映射仍见[持久回执交接](handoff/2026-11-03-r18-device-call-safety.md)。
- 旧 `dial.json` 留作备份/回退，不读取其中的 `quiet_until` 约束新拨号；新的 `operations.json` 保存持久回执，不清空配对、短信或原系统。

## 对端挂断通知链

```text
对端挂断/拒接 → U30 基带原生结束事件 → 原生 mu300-atd 日志
             → Agent 校验原通话 ID + 新鲜通话列表
             → active=null、原通话 history.state=ended、revision 增加
             → 原有 AirSIM 状态/事件长轮询收到终态，客户端自行结束界面
```

本次修复了一个可复现的代码时序缺口：基带先报告 `^DSCI` 结束，但下一次 CLCC 暂时仍有通话行，旧代码会消耗并丢弃结束提示，随后空列表需要走完整的缺失宽限期。

现在：

1. 结束提示绑定缓存中的 UUID、槽位、方向，最多保留 5 秒。这是提示的有效期，不是挂断后的等待时间。首次成功 CLCC 确认该槽消失，即立即结束并通知；仍在列表中时不强行结束。
2. CLCC 查询前后都读取原生新事件，查询过程中到达的结束事件可以在同一轮生效。查询失败不能直接产生终态。
3. 同槽的新进展事件、UUID 替换、日志轮换/截断/损坏/不可读或提示到期，会清除旧提示；旧事件不能结束新通话。首次启动不回放历史日志。无可信事件时保留原有保守轮询宽限。
4. 发布明确 `ended`、原 ID 与结束时间，唤醒既有状态/事件长轮询；已结束已知通话再次请求挂断为空闲幂等成功，不向基带补发挂断命令。
5. 固定日志分别记录 native termination observed、terminal state published 与 attempting ATD once，便于人工测试核对时序和命令次数；不记录号码、请求体、短信或音频。日志不等于客户端已收到的证据。

没有擅自接听、拨号、代挂、修改基带配置或直接打开串口；同一基带仍由 mu300-atd 管理。上述代码缺口不是对此前所有实机延迟来源的证明，需同步采样验收。

## 测试与安装边界

fixture 回归覆盖：原通话结束后立即重拨同号并分配新 UUID；旧请求不重拨、不影响新电话；旧未来 quiet_until 不再阻塞；无编号请求拒绝；未知提交不重发；并发/HTTP 重试；结束事件早于、同时于 CLCC 更新；瞬态查询失败；事件过期、进展反转、槽复用和日志轮换；结束通知唤醒长轮询。持久回执、签名和只读查询继续沿用原有回归。

签名候选包生成后按已有授权在空闲 U30 Air 备份、更新服务；实际安装状态记录在本机候选报告。只有用户手动测试对端拒接、接通后对端挂断、立即重新拨号以及双向音频后，才能更新实机结论。本轮不改 iOS/Android 客户端，不解除 R18 的发布暂停。

## 历史问题与其他边界

旧候选确实误伤了手动重拨；此前用户反馈结束最终发生但延迟明显。过去观察窗口未覆盖实际拒接瞬间，不能把总通话时长当作挂断延迟。本次用新的时序回归与后续现场采样分别验证。

客户端曾报告 0.9.8（158）。另一个线程负责客户端改进，本线程只读参考其交接，不把未安装的新客户端当作用户已在使用的版本。

运营商接通前语音（early media）仍未支持，本次不添加假公告、不伪造 active/已接通。短信的两分钟重复发送保护是独立功能，未受本次通话修改影响。

## 2026-11-03 实机反馈：结束延迟未通过

已安装 `ce198d0`，用户确认对方很快拒接，自己没有点击 AirSIM 挂断；手机约 40 秒后才以“未接通”错误结束。此项验收为 **FAIL**，仍暂停发布。

脱敏记录显示三次拨号回执耗时 448/443/559 ms，原生结束被 Agent 观察到后，两条事件接口均在同一秒返回 `active=null` 和原通话 `ended`。其中没有挂断 HTTP 请求的一通，从拨号回执到原生终态约 38.5 秒；此前缺少人工拒接瞬间的同步标记，不能把这一时长直接作为精确拒接延迟，更不能宣称手机及时收到了通知。

补充只读采样覆盖 `^CEND`、`+EARLYMEDIA` 和有限的结束原因数字字段，以区分基带继续报告 alerting 与客户端收尾延迟。接通前媒体不是拒接证明，不能据此主动挂断。此次诊断不修改客户端、基带配置或通话控制代码，不拨号、不代挂、不录音。

### 同步拒接采样结果

本次新增采样使用主机 UTC 时钟（2026-11-02，本地日期为 11-03）：

- `17:21:49.236`：拨号回执，459 ms；随后状态为 `alerting`。
- `17:21:54.313`：观察到 `+EARLYMEDIA: 1`。只证明接通前媒体指示，不证明忙线、拒接或公告内容，未录音。
- `17:22:01`：收到用户“已拒接”消息；实际操作早于消息到达，不能将消息到达当成精确拒接时刻。
- `17:22:17.757`：通过现有 mu300-atd 单次只读 `AT+CLCC` 查询成功，仍返回 `[slot=1,dir=0,state=3,mode=0,mpty=0]`，即基带仍报告呼叫中。
- `17:22:24`：原生日志才出现 `^DSCI` 结束、`NO CARRIER`、`^CEND`；`17:22:24.558`，Agent 通话事件接口返回 revision 14、原通话 ended。该通观察窗口没有挂断 HTTP 请求。

这次至少存在“用户拒接消息到达后约 23 秒，基带仍未释放”的延迟，不能通过缩短 Agent 空列表宽限来消除；期间根本不是空列表。接通前媒体可能与等待网络释放有关，但尚无证据证明音频内容或运营商根因。仍需更早且可信、可关联该通电话的拒接信号，不能把所有 early media 当成失败或用固定倒计时误挂正常通话。尚未实现对此延迟的有效修复。

### 手机已收到响应，但界面未收尾

用户进一步确认：设备结束后 AirSIM 仍继续计时。已只读读取已配对测试 iPhone 的现成 `agent-verbose-trace.json`，仅保留本次通话的接口、阶段、时间、耗时和 HTTP 状态；原始临时文件自动删除，未读取联系人、短信或通话历史文件，未安装、启动或修改 App。

手机追踪记录 `/api/events` 在 `17:22:24.630Z`、`/api/calls/events` 在 `17:22:24.649Z` 完成 HTTP 200。与设备 `17:22:24.558Z` 的终态响应在同一秒；两端时钟有小偏差，不据此宣称精确网络耗时。设备原始回执与终态在内存中比对，`backend_id`、`android_id` 均一致，`state=ended`，结束时间完整。

这可排除该轮“结束响应被网络继续拖住几十秒”的解释，但现成手机追踪没有记录解码后的状态、Router 接受/拒绝或界面清理步骤，尚不能指定具体客户端代码根因。对应证据已交给用户指定的 AirSIM 线程；本工作树不修改客户端。基带释放较晚与客户端收到响应后未收尾是两段问题，不能将其中之一解释为全部原因。
